# Авторизация администратора — предложение контракта

Дата: 24.10.2026. Статус: проект для реализации пользователем; API ещё нет.
Основание: [выбранные решения](superpowers/plans/планы.md#админ-панель-выбранные-решения).
Go, SQL и конфигурацию сервера реализует пользователь; ассистент подключает интерфейс.

## Границы этапа

Вход через Steam OpenID 2.0, проверка разрешённых SteamID64, постоянная
серверная сессия, получение текущего администратора, выход и отзыв всех сессий.
Аккаунты импортера, Steam Guard для GC, очередь и демки — отдельные этапы.

Сохраняем выбранный в плане вариант: случайный непрозрачный токен в cookie,
сессия в PostgreSQL. Он позволяет отзывать вход и сохранять его после перезапуска.
Самодостаточный JWT потребовал бы отдельного механизма немедленного отзыва;
сессия только в памяти не переживает перезапуск.

## Конфигурация

Предлагаемые новые переменные:

- `PUBLIC_BASE_URL`: доверенный внешний адрес сайта, без завершающего `/`.
  Из него строятся realm, callback и ожидаемый Origin; не из заголовка Host.
- `ADMIN_STEAM_IDS`: список разрешённых SteamID64 через запятую.
  Пустой список запрещает административный доступ. Некорректная конфигурация
  должна обнаруживаться при запуске. SteamID64 не является Dota Account ID.

Список загружается при запуске: изменение env требует перезапуска.
После перезапуска каждый запрос сверяется с новым списком, даже если cookie действительна.
Никакого автоматического назначения первого вошедшего администратором.

Согласованный абсолютный срок сессии — 15 дней от момента авторизации,
без продления при запросах. Начальный список SteamID64 пока не задан.

## Маршруты

| Метод и путь | Назначение | Успех |
| --- | --- | --- |
| `GET /auth/steam` | Создать попытку входа и перенаправить в Steam | `302` |
| `GET /auth/steam/callback` | Проверить ответ Steam, права, создать сессию | `303` на `/` |
| `GET /api/admin/session` | Текущий администратор и CSRF-токен | `200`, JSON ниже |
| `POST /api/admin/logout` | Отозвать текущую сессию и удалить cookie | `204` |
| `POST /api/admin/logout-all` | Отозвать все сессии этого SteamID64, включая текущую | `204` |

Пока экран админки не существует, callback ведёт на `/`; после появления экрана
заменим фиксированный адрес. Произвольный внешний `return_to` не принимается.
Неподдерживаемые методы — `405` с правильным `Allow`.
API возвращает JSON, а не перенаправление на HTML входа.

```json
{
  "admin": {
    "steam_id": "76561198000000000"
  },
  "expires_at": "2026-11-08T12:00:00Z",
  "csrf_token": "<токен, привязанный к текущей сессии>"
}
```

SteamID64 — строка; время — RFC 3339 UTC. Ник и аватар не обязательны на этом
этапе: недоступность API профилей не должна мешать входу.

Ошибки используют существующий `handlers.WriteError`:

```json
{"error":{"code":"unauthenticated","message":"Требуется вход через Steam"}}
```

- `401 unauthenticated`: cookie отсутствует, неизвестна, истекла или отозвана.
- `403 admin_required`: личность подтверждена, но SteamID64 не разрешён.
- `403 csrf_invalid`: отсутствует или неверен CSRF-токен либо Origin.
- `400 steam_auth_invalid`: некорректный, просроченный или повторный callback.
- `400 steam_auth_cancelled`: пользователь отменил вход в Steam.
- `502 steam_auth_unavailable`: Steam не удалось проверить; сессию не создавать.
- `500 internal_error`: ошибка БД; доступ не предоставлять.

Для callback до появления интерфейса ошибок достаточно ответа с этим JSON.
Для неразрешённого пользователя сессия администратора не создаётся.
Ответы авторизации и административного API: `Cache-Control: no-store`.

## Проверка входа

Использовать реализацию OpenID 2.0 с проверкой протокола; парсинг SteamID из
параметра callback сам по себе ничего не подтверждает.

1. Создать случайную одноразовую попытку входа со сроком, например, 10 минут.
   Привязать её к браузеру отдельной короткоживущей HttpOnly-cookie и к
   ожидаемому `return_to`. Значение корреляции не является токеном сессии.
2. Направить пользователя к фиксированному провайдеру Steam.
3. В callback проверить привязку к браузеру и попытке входа, `return_to`,
   namespace, mode, OP endpoint, соответствие identity и claimed_id,
   обнаруженные данные провайдера, обязательные подписанные поля, подпись
   и свежесть/уникальность `response_nonce` по правилам OpenID 2.0.
   При прямой проверке подписи обращаться только к доверенному Steam endpoint,
   с сетевым таймаутом. Не отправлять проверку на URL из непроверенного callback.
4. Атомарно исключить повторное использование попытки и nonce.
   Проверить SteamID64 по серверному списку, затем создать новый токен сессии.
   При замене существующей сессии браузера отозвать её старый токен.
5. Удалить cookie попытки входа и установить cookie сессии.

Для OpenID достаточно подтверждённого SteamID64. Пароль Steam на сайте не
запрашивается. Вход на сайт не предоставляет импортеру доступ к Steam/GC.

## Сессии и CSRF

- Токен сессии: 32 случайных байта из криптографического генератора, кодирование
  base64url. В БД хранить SHA-256 токена, SteamID64, время создания,
  абсолютное истечение и признак/время отзыва; исходный токен не сохранять.
- Cookie: `__Host-dota_admin`, `Path=/`, `Secure`, `HttpOnly`, `SameSite=Lax`,
  без `Domain`, с `Max-Age`/`Expires` в пределах срока сессии.
  Для локальной проверки нужен HTTPS; production-cookie не ослаблять.
- На каждом административном запросе проверять сессию и актуальный allowlist.
  Оба POST выхода также требуют этой проверки.
- CSRF-токен привязан к сессии и возвращается через `/api/admin/session`.
  Его можно хранить на сервере или вычислять HMAC с отдельным серверным секретом;
  выбранный способ должен переживать перезапуск и поддерживать постоянную сессию.
  Клиент передаёт его в `X-CSRF-Token` на изменяющих запросах.
  Проверять также `Origin` на точное совпадение с настроенным origin;
  для этих браузерных POST отсутствие Origin отклонять.
- Не разрешать сторонним origin доступ к административному API через CORS.
  Секрет сессии не передавать в JSON, URL или localStorage. Не логировать cookie,
  CSRF-токены и полный callback query. SameSite не заменяет CSRF-проверку.
- Выход сначала фиксирует отзыв в БД, затем удаляет cookie с теми же атрибутами.
  Отзыв всех сессий включает текущую. При ошибке БД не сообщать об успешном отзыве.

## Хранение и размещение в проекте

Предлагаемое разделение ответственности, без обязательных имён файлов:

- `internal/config`: внешний URL и allowlist.
- `internal/auth`: OpenID, генерация/проверка токенов и правила доступа.
- `internal/repository/postgres`: попытки входа, использованные nonce и сессии.
- `internal/http/handlers`: обработчики пяти маршрутов.
- `internal/http`: middleware проверки администратора и CSRF, регистрация маршрутов.
- `migrations/005_admin_auth.*.sql`: новые таблицы и индексы после существующей 004.

Попытки входа и использованные nonce сохранять в PostgreSQL, с уникальными
ограничениями и атомарным потреблением для защиты от параллельных callback.
Удалять их после защитного окна; не удалять nonce, пока соответствующий ответ
ещё может пройти проверку свежести. Истёкшие сессии тоже можно очищать отдельно.

По текущей документации деплоя роль `dota_web` имеет только чтение.
Для новых auth-таблиц нужны ограниченные права SELECT/INSERT/UPDATE/DELETE
и права на последовательности, если они используются. Права записи в таблицы
матчей для этого этапа не требуются. Реальные права на VPS нужно проверить отдельно.

## Порядок реализации и приёмка

1. Конфигурация и миграция auth-таблиц.
2. Репозиторий сессий: создание, поиск по хешу, истечение, отзыв одной/всех.
3. Middleware и три `/api/admin/*` маршрута.
4. OpenID start/callback и подключение к созданию сессии.
5. Проверка в браузере по HTTPS и автоматические тесты пограничных случаев.

Готовность: разрешённый SteamID входит; посторонний не получает доступ;
поддельный callback, повторный nonce, чужая/истёкшая попытка входа отклоняются;
без cookie API даёт 401; истёкшая/отозванная сессия не работает;
POST без CSRF или с чужим Origin отклоняется; оба выхода отзывают нужные сессии;
после перезапуска действительная сессия сохраняется;
после удаления SteamID из конфигурации и перезапуска доступ исчезает;
при недоступности БД/Steam вход не происходит.
