# Плашки сайта — проект контракта

Дата: 25.10.2026. Статус: предложение для следующего этапа; API пока не реализован.
Go, миграции и маршруты реализует пользователь; интерфейс — ассистент.

## Поведение

Администратор создаёт плашки, меняет текст, удаляет записи.
Все сохранённые плашки видны посетителям на главной странице и странице матча.
Список общий для обеих страниц, сортировка: ID по убыванию (новые записи первыми).
Пустой список означает отсутствие плашек. Дата, если нужна, вписывается администратором
прямо в текст. Отдельного поля даты в БД, API и форме нет; сервер не разбирает дату
из текста и не использует её для сортировки или расписания публикации.

Первая версия использует обычный текст без HTML, Markdown, вложений и ссылок.
Интерфейс вставляет текст через textContent. После изменения сохраняется результат в БД;
на уже открытых публичных страницах он появляется после обновления страницы.

Выбранное направление: отдельная таблица и CRUD API, встроенные в текущий Go-сервер.
Редактирование HTML требует нового деплоя; одна запись настроек не подходит для списка
плашек с независимым редактированием и удалением. Новые настройки окружения не нужны.

## Запись

```json
{
  "id": "1",
  "text": "Обновили статистику матчей — 25.10.2026"
}
```

ID — строка с положительным целым в диапазоне PostgreSQL bigint.
Текст после strings.TrimSpace содержит от 1 до 500 Unicode-символов
(в Go считать через utf8.RuneCountInString); в БД сохраняется обрезанный текст.

## Маршруты

| Метод и путь | Доступ | Успех |
| --- | --- | --- |
| GET /api/notices | Все посетители | 200, объект с массивом items |
| GET /api/admin/notices | Администратор | 200, такой же список |
| POST /api/admin/notices | Администратор + CSRF | 201, созданная запись |
| PUT /api/admin/notices/{id} | Администратор + CSRF | 200, обновлённая запись |
| DELETE /api/admin/notices/{id} | Администратор + CSRF | 204, без тела |

Ответ списка:

```json
{"items": []}
```

POST и PUT принимают одинаковое тело; PUT полностью заменяет текст:

```json
{
  "text": "Обновили статистику матчей — 25.10.2026"
}
```

Поле text обязательно. Неизвестные поля, null, неверные типы, несколько JSON-значений
и некорректный JSON отклоняются. Лимит тела — 8 КиБ; Content-Type — application/json
с допустимым параметром charset. ID генерирует сервер; клиент не отправляет его в теле.
Если запись уже удалена, PUT и DELETE возвращают 404.
Одновременные изменения: сохраняется последнее успешно выполненное обновление.

## Авторизация и ошибки

Административные маршруты используют существующий SessionFromRequest.
POST, PUT и DELETE дополнительно используют CheckCSRF с Origin и X-CSRF-Token.
GET не меняет данные и не требует CSRF. Все ответы этого этапа — Cache-Control: no-store;
JSON-ответы — Content-Type: application/json. API не перенаправляет на вход.

Ошибки через существующий WriteError:

```json
{"error":{"code":"invalid_request","message":"Текст плашки обязателен"}}
```

| HTTP | code | Причина |
| --- | --- | --- |
| 400 | invalid_request | Неверное тело, поле или ID |
| 401 | unauthenticated | Нет действующей сессии |
| 403 | admin_required | Нет прав администратора |
| 403 | csrf_failed | Отказ существующей проверки CSRF |
| 404 | notice_not_found | Запись отсутствует |
| 405 | method_not_allowed | Неподдерживаемый метод; вернуть Allow |
| 413 | request_too_large | Тело больше 8 КиБ |
| 415 | unsupported_media_type | Неподдерживаемый Content-Type |
| 500 | internal_error | Ошибка сервера без деталей SQL в ответе |

## Хранение и порядок реализации

Предлагаемая таблица public.site_notices:

- id — bigint GENERATED ALWAYS AS IDENTITY, первичный ключ;
- text — text NOT NULL, CHECK длины обрезанного текста от 1 до 500.

Миграция 007 создаёт таблицу; down удаляет её. Текущая HTML-плашка автоматически
не переносится: её можно добавить через админку до переключения публичного интерфейса.
В deploy/migrate.sh нужно добавить права SELECT, INSERT, UPDATE, DELETE на новую
таблицу и USAGE на identity-последовательность для роли приложения. Текущие гранты
для таблиц авторизации не предоставляют эти права автоматически.

Порядок: миграция → repository → DTO и handlers → маршруты и права приложения →
проверка API → редактор в админке и замена статических плашек на обеих страницах.
При ошибке публичного GET интерфейс не восстанавливает старую HTML-плашку.

Готовность: создать две плашки, проверить порядок и обе страницы; изменить одну;
удалить обе и получить items: []; проверить сохранение после перезапуска,
отказы без сессии/CSRF и ошибки валидации. Проверки прав БД выполняются под ролью
приложения, а не только под владельцем базы.
