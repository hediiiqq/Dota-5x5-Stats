# Первый этап: история покупок

Статус: проект контракта для согласования. Серверный маршрут и интерфейс пока
не реализованы. Бэкенд пишет пользователь, фронтенд — ассистент.

Цель этапа: на странице матча показывать покупки выбранного игрока с иконкой,
названием предмета и игровым временем. Показать отрицательные времена до начала
игры. Снимки инвентаря, передачи и сборки предметов — следующий отдельный этап.

## Предлагаемый маршрут

`GET /api/matches/{id}/purchases`

`id` — внутренний ID матча, как в существующем `GET /api/matches/{id}`.
Это не Dota match ID.

Пример структуры ответа (внутренний ID условный; показаны две покупки):

```json
{
  "match_id": "123",
  "dota_match_id": "9040846950",
  "available": true,
  "players": [
    {
      "player_slot": 0,
      "purchases": [
        { "item_id": 44, "time": -89 },
        { "item_id": 34, "time": -89 }
      ]
    }
  ]
}
```

## Правила данных

- `match_id` и `dota_match_id` — строки; первый совпадает с существующим полем
  `id` ответа матча, второй — с его `dota_match_id`.
- `available=true` означает, что данные покупок импортированы; это не обещание
  наличия остальных метаданных, MVP или демок.
- `players` содержит записи с уникальным `player_slot`. Для этого матча
  используются слоты 0–4 и 128–132. Ники, герои и Account ID фронтенд берёт
  из существующего ответа матча, сопоставляя по `player_slot`.
- `item_id` — числовой ID предмета. Название и иконку фронтенд берёт из
  существующего справочника; неизвестный ID показывает как «Предмет #ID».
- `time` — целое знаковое число секунд относительно начала игры.
  `-89` отображается как `−1:29`, `0` как `0:00`, `98` как `1:38`.
- Сохранять повторные покупки, даже если ID и время совпали. Не объединять
  их в один предмет и не терять исходный порядок одинаковых времён.
- `purchases=[]` — известная пустая история конкретного игрока.
  `purchases=null` — история этого игрока недоступна. Отсутствующую запись
  игрока фронтенд также трактует как недоступные данные.
- Сервер может вернуть историю в исходном порядке. Фронтенд сортирует по
  времени с сохранением исходного порядка при одинаковом времени.
- При отсутствии метаданных существующего матча вернуть HTTP 200,
  `available=false` и `players=[]`, с теми же ID матча.
- Для неизвестного матча — HTTP 404 в существующем формате ошибок.
  При серверной ошибке — HTTP 5xx, а не `available=false`.

## Фронтенд этого этапа

- Отдельный блок «Покупки» на странице матча; выбор игрока из состава матча.
- Хронологическая лента предметов с временем и подсказкой названия.
- Состояния загрузки, ошибки с повтором, недоступных данных и пустой истории.
- Ошибка покупок не скрывает основную страницу матча.
- Не называть записи таймингами появления в инвентаре, сборки или передачи:
  источник `items.purchaseTime` описывает покупки.

## Проверка этапа

Матч 9040846950: всего 673 покупки, 86 до начала игры; у слота 0 — 91 запись,
первые покупки item 44 и item 34 на −89 секунде. Полную историю нужно
сохранить без сокращения. Проверить также неизвестный предмет, повторные
покупки, отсутствие метаданных и сетевую ошибку.

Следующий шаг: пользователь проверяет предлагаемый контракт. После согласования
он реализует маршрут и хранение, ассистент — фронтенд на примерах ответов,
затем подключает реальный API. Go-код и миграции ассистент не пишет.
