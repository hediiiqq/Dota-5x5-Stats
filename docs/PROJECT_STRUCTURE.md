# Структура проекта Dota Stats: назначение файлов

Дата: 12 октября 2026 года.

Это описание предложенной структуры, а не перечень уже реализованных файлов. Корень будущего репозитория обозначен как `dota-stats/`. Создавать все файлы заранее не требуется: они добавляются по мере выполнения плана.

Бэкенд на Go реализует владелец проекта. Фронтенд в `web/` реализует Codex. Формат API и правила расчёта статистики согласуются вместе.

## 1. Точки входа — cmd/

### cmd/server/main.go

Главная точка запуска серверного приложения.

- Загружает конфигурацию и настраивает логирование.
- Открывает подключение к PostgreSQL.
- Создаёт репозитории, сервисы, обработчики и маршрутизатор.
- Подключает источники импорта, когда они реализованы.
- Запускает HTTP-сервер и фоновый обработчик заданий.
- При завершении приложения останавливает приём запросов и освобождает ресурсы.

Этот файл связывает готовые части приложения. SQL-запросы, разбор демок и расчёты статистики находятся в соответствующих пакетах.

### cmd/gc-check/main.go

Отдельная утилита для проверки интеграции с Game Coordinator до подключения к сайту.

- Использует настройки подключения аккаунта.
- Устанавливает сессию Steam/GC.
- Запрашивает известный матч или историю с включёнными practice-матчами.
- Выводит диагностический результат и при необходимости сохраняет обезличенный пример ответа.
- Завершает работу при таймауте или ошибке.

Позволяет проверять источник независимо от HTTP-сервера, базы и фронтенда. Использует общий клиент из `internal/source/coordinator`, чтобы не дублировать интеграцию.

## 2. Настройки — internal/config/

### internal/config/config.go

Описывает структуру конфигурации и её загрузку из окружения.

Предполагаемые настройки: адрес HTTP-сервера, подключение к базе, каталог демок, предел загрузки, таймауты, количество работников импорта и настройки аккаунтов координатора.

Проверяет обязательные параметры и возвращает понятную ошибку при неправильной конфигурации. Секреты не должны попадать в диагностический вывод.

## 3. Общие модели — internal/domain/

Этот пакет описывает данные проекта независимо от HTTP, PostgreSQL, go-dota2 и Manta.

### internal/domain/match.go

Содержит модель матча и участия игрока в конкретном матче, например `Match` и `MatchPlayer`.

- Матч: идентификаторы, время начала, длительность, статус результата, победившая сторона, режим и составы.
- Участие: игрок, герой, сторона, K/D/A и дополнительные подтверждённые показатели.
- Отсутствующие показатели должны отличаться от реального нуля.

Здесь можно размещать небольшие правила модели, например проверку допустимой стороны. Получение данных и сохранение в БД выполняются другими пакетами.

### internal/domain/player.go

Описывает участника группы: внутренний ID, отображаемое имя и связь с игровым аккаунтом.

Участник группы и его участие в матче — разные сущности. Один участник может играть много матчей и менять сторону; имя в конкретном матче может отличаться от текущего имени участника. Стабильные идентификаторы используются для сопоставления, ник — для отображения.

### internal/domain/import_job.go

Описывает задание импорта: ID, источник, состояние, время создания и обновления, связанный матч после завершения и сведения об ошибке.

Предлагаемые состояния: `queued`, `processing`, `completed`, `failed`.

Модель позволяет API и фоновому работнику одинаково понимать состояние импорта. Она не запускает горутины самостоятельно.

## 4. HTTP API — internal/http/

### internal/http/router.go

Регистрирует URL, HTTP-методы, обработчики и middleware.

Примеры маршрутов: `/api/health`, `/api/matches`, `/api/matches/{id}`, `/api/players`, `/api/players/{id}`, `/api/imports/replay`, `/api/imports/gc`, `/api/imports/{id}`.

Маршрутизатор направляет запрос в обработчик. Конкретный формат ответа определяется контрактом API.

### internal/http/handlers/matches.go

Обрабатывает запросы списка матчей и одного матча.

- Читает ID, фильтры и параметры пагинации.
- Проверяет входные данные.
- Вызывает сервис матчей.
- Преобразует результат в DTO и отправляет JSON.
- Выбирает HTTP-код, например `400` для неверного параметра или `404` для отсутствующего матча.

Обработчик работает с HTTP; запросы в базу находятся в репозитории.

### internal/http/handlers/players.go

Обрабатывает список участников, страницу одного участника, его сводную статистику и при необходимости историю его матчей.

Проверяет ID и период выборки, обращается к сервисам, формирует ответы по контракту. Правила расчёта побед и винрейта находятся в сервисе статистики.

### internal/http/handlers/imports.go

Принимает запросы импорта и возвращает состояние задания.

- Для демки проверяет загрузку, формат и предел размера файла.
- Для координатора проверяет параметры запроса.
- Передаёт создание задания сервису импорта.
- Возвращает ID принятого задания; длительный разбор не выполняется внутри запроса.
- По ID задания возвращает состояние, ошибку или ссылку на полученный матч.

Временное хранение принятого файла и его дальнейшая очистка должны иметь явно назначенного владельца в реализации.

### internal/http/dto/

Папка для структур JSON-запросов и ответов. В исходной схеме отдельные файлы внутри неё ещё не названы.

DTO задают публичный формат данных: имена полей, строковые внешние 64-битные ID, даты, `null` для отсутствующих показателей, списки, пагинацию и ошибки.

Они позволяют изменять внутренние модели или схему базы без случайного изменения API. Типы protobuf напрямую фронтенду не выдаются.

### internal/http/middleware/

Папка для общих функций вокруг обработчиков; отдельные файлы добавляются при реализации.

Возможные задачи: логирование запросов, ID запроса, проверка сессии и права импорта, восстановление после паники. CORS добавляется, если выбранное размещение фронтенда требует запросов с другого origin.

## 5. Правила приложения — internal/service/

### internal/service/matches.go

Предоставляет сценарии получения одного матча и истории группы.

Принимает понятные параметры — ID, фильтры, пагинацию; вызывает репозиторий и возвращает модели или ошибки приложения. Здесь определяется поведение вроде «матч не найден». Сервис не зависит от HTTP-кодов.

### internal/service/statistics.go

Определяет правила сводной статистики: какие матчи входят в выборку, как считать победы, поражения, винрейт и средние K/D/A, как учитывать неполные данные.

Агрегаты можно получать SQL-запросами из репозитория, но смысл показателей и состав выборки должны оставаться явными. В ответе требуется число матчей, на которых основан показатель.

### internal/service/imports.go

Управляет сценарием импорта.

- Создаёт задания и предоставляет их состояние.
- Организует преобразование результата источника в общую модель.
- Проверяет, существует ли уже такой матч.
- Применяет согласованные правила дополнения и конфликта данных.
- Организует атомарное сохранение матча и участников.
- Обновляет результат задания.

Работник отвечает за выполнение очереди, а сервис — за правила самого импорта. Точный ключ сопоставления источников определяется по реальным данным.

## 6. Источники — internal/source/

### internal/source/coordinator/client.go

Обёртка над подключением к Steam и Game Coordinator.

Управляет жизненным циклом сессии: подключение, авторизация, готовность GC, события соединения, завершение и восстановление соединения по выбранной политике. Зависимости go-steam/go-dota2 используются здесь.

Предоставляет остальному пакету готовый клиент, не раскрывая учётные данные фронтенду.

### internal/source/coordinator/requests.go

Реализует запросы истории и подробностей матча через готовую сессию GC.

Использует соответствующие сообщения protobuf, сопоставляет ответы, задаёт таймауты и проверяет результат запроса. Для истории включает `include_practice_matches`, когда запрашиваются матчи лобби.

Наличие сообщений в схемах не гарантирует работу конкретного запроса: актуальные ID сообщений, ответы и доступность приватных матчей проверяются через `gc-check`.

### internal/source/coordinator/mapper.go

Преобразует структуры ответа координатора в `domain.Match` и связанные данные.

Сопоставляет игроков и стороны, приводит единицы измерения, сохраняет отсутствие необязательных полей. Здесь заканчивается зависимость основной модели приложения от protobuf-типов координатора.

### internal/source/replay/parser.go

Открывает или принимает поток демки и запускает Manta.

Регистрирует callbacks, собирает нужные события и данные, возвращает промежуточный результат. Повреждённый или неподдерживаемый файл должен приводить к контролируемой ошибке. Доступность показателей проверяется на настоящих демках.

### internal/source/replay/mapper.go

Преобразует собранные парсером данные в общую модель матча.

Определяет доступные ID, игроков, стороны, результат и показатели. Здесь удобно отделить финальные значения от расчётов по событиям и сохранить сведения о происхождении данных. Слияние с уже существующей записью выполняет сервис импорта.

## 7. Хранение — internal/repository/

### internal/repository/interfaces.go

Описывает операции, которые нужны сервисам от хранилища: получить матч, найти историю, сохранить матч с игроками, получить участников, создать и обновить задание.

Интерфейсы должны быть небольшими и определяться реальными потребностями. Атомарное сохранение можно выразить отдельной операцией репозитория; не нужно выдавать SQL-транзакцию HTTP-обработчику.

### internal/repository/postgres/db.go

Открывает и проверяет подключение к PostgreSQL, настраивает пул соединений и предоставляет способ его закрытия.

Получает настройки от `config`. Миграции должны запускаться выбранным явно способом; открытие подключения само по себе не означает обновление схемы.

### internal/repository/postgres/matches.go

Содержит SQL для матчей и участия игроков: чтение одного матча, история с фильтрами, сохранение, обновление и проверка идентификаторов.

Использует параметризованные запросы и обеспечивает согласованный способ атомарной записи матча с игроками. Ограничения базы дополнительно защищают от дублей при одновременном импорте.

### internal/repository/postgres/players.go

Содержит SQL для участников и связей с игровыми аккаунтами. Может выполнять запросы агрегатов по правилам, установленным сервисом статистики.

Поиск по нику не должен автоматически считаться доказательством того, что найден тот же игрок.

### internal/repository/postgres/import_jobs.go

Хранит задания импорта и изменения их статуса.

Предоставляет создание, получение, выбор следующего задания и обновление результата. При нескольких работниках выбор задания должен исключать двойную обработку. После перезапуска зависшие задания должны разрешаться по согласованной политике.

## 8. Фоновая обработка — internal/worker/

### internal/worker/imports.go

Выполняет задания вне HTTP-запроса.

Получает задания, ограничивает число одновременных обработок, передаёт работу сервису импорта и реагирует на остановку приложения. Координатор и демки могут иметь разные ограничения параллелизма.

Состояние задания хранится в базе; горутина — механизм выполнения, а не единственное место хранения очереди.

## 9. Миграции — migrations/

### migrations/001_initial.up.sql

Создаёт первую версию схемы: таблицы матчей, игроков, участия и заданий импорта, необходимые ключи, ограничения и индексы.

Этот файл фиксирует первоначальную структуру. После применения на рабочей базе изменения оформляются новыми миграциями.

### migrations/001_initial.down.sql

Описывает откат первой миграции в обратном порядке зависимостей.

Откат с удалением таблиц уничтожает их данные; это средство управления схемой, которое требует осознанного применения.

## 10. Фронтенд — web/

В исходной структуре обозначены папки, но конкретные файлы фронтенда ещё не выбраны. Их имена и расширения зависят от согласованного стека.

### web/src/pages/

Страницы истории матчей, подробностей матча, участника и импорта. Каждая страница собирает компоненты, выполняет нужные запросы и показывает загрузку, данные, пустое состояние или ошибку.

### web/src/components/

Переиспользуемые элементы интерфейса: таблица игроков, карточка матча, фильтры, форма загрузки, пагинация и сообщение об ошибке.

### web/src/api/

Функции запросов к Go API. Здесь находятся адрес сервера, отправка параметров и файлов, чтение ответов и единая обработка ошибок. Подключения к Steam и координатору здесь нет.

### web/src/types/

Описание типов ответов и запросов, если используется TypeScript. Типы соответствуют `docs/api.md` и backend DTO, включая строковые ID и nullable-показатели.

### web/src/styles/

Общие стили: цвета, типографика, таблицы, формы и адаптация к телефону. Способ организации стилей определяется фронтенд-стеком.

### web/public/

Статические файлы, доступные браузеру: например favicon и изображения. Секреты, настройки аккаунтов и пользовательские демки здесь не хранятся.

## 11. Документация — docs/

### docs/api.md

Контракт между бэкендом и фронтендом.

Для каждого маршрута описывает метод, путь, параметры, тело запроса, успешный ответ, ошибки, право доступа и примеры JSON. Также фиксирует единицы измерения, формат времени, статусы импорта, пагинацию и правила отсутствующих полей.

Согласованное изменение контракта позволяет обеим сторонам развиваться параллельно.

### docs/roadmap.md

План этапов, границы MVP, распределение задач и критерии готовности. Не заменяет API-контракт.

Сейчас дорожная карта и учебный план сохранены в корне рабочей области как `ROADMAP.md` и `PROJECT_PLAN.md`. При оформлении репозитория можно перенести их в `docs/`, выбрав одно основное место хранения.

## 12. Примеры данных — testdata/

Папка для обезличенных примеров ответов координатора, результатов парсинга и небольших проверочных файлов. Она помогает воспроизводить ошибки и работать без постоянного подключения к источнику.

Отдельные файлы в исходной схеме не названы. Большие демки требуют отдельного решения по хранению; учётные данные не включаются в примеры.

## 13. Файлы корня

### .env.example

Перечень настроек с безопасными примерами или пустыми значениями: адрес сервера, подключение к базе, каталог файлов, таймауты и ограничения.

Это образец конфигурации. Само наличие файла не заставляет Go загружать `.env`: механизм загрузки выбирается явно. Реальные секреты в этот файл не записываются.

### .gitignore

Определяет локальные и генерируемые файлы, которые не должны попадать в Git: реальные `.env`, бинарники, каталоги зависимостей фронтенда, сборки, логи и загруженные демки.

Пути исключений подбираются под реализацию. Примеры тестовых данных, которые нужны проекту, должны оставаться доступными в репозитории.

### go.mod

Описывает имя Go-модуля, требуемую версию Go и зависимости. Обновляется инструментами Go при добавлении и приведении зависимостей в порядок.

### go.sum

Содержит контрольные суммы содержимого зависимостей Go. Формируется инструментами Go и хранится в Git вместе с `../go.mod`. Версии зависимостей задаются в `go.mod`; `go.sum` не заменяет его.

### README.md

Главная инструкция проекта: назначение сайта, зависимости, настройка окружения, создание базы, применение миграций, запуск бэкенда и фронтенда, проверки и ссылки на документацию.

По README другой участник должен суметь запустить проект локально.

## Как части работают вместе

Обычный запрос:

```text
web/src/api
    → internal/http/router
    → internal/http/handlers
    → internal/service
    → internal/repository/postgres
    → PostgreSQL
```

Импорт:

```text
Форма импорта
    → HTTP handler
    → service создаёт задание
    → repository сохраняет задание
    → worker забирает его
    → service использует coordinator или replay
    → mapper формирует domain.Match
    → service применяет правила объединения
    → repository сохраняет матч и результат задания
    → фронтенд получает статус и открывает матч
```

## Что создавать первым

1. `../go.mod` — отдельный модуль.
2. `internal/domain/match.go` — учебный матч и десять игроков.
3. `../cmd` — запуск простого сервера.
4. `internal/http/router.go` и `handlers/matches.go` — маршрут тестового матча.
5. Структуры в `internal/http/dto/` — согласованный JSON.
6. `docs/api.md` — примеры ответов и ошибки.

На этом этапе допустимо собрать простой пример без всех слоёв. Репозитории, сервисы импорта и работники добавляются при появлении соответствующих задач. Проверки поведения размещаются рядом с реализацией в файлах `*_test.go`; в первоначальном дереве они не перечислены.
