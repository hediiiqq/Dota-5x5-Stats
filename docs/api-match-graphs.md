# Графики матча — контракт API

Статус на 23.10.2026: эндпоинт, маппер и интерфейс реализованы. Пользователь
разрешил ассистенту завершить бэкенд и фронтенд этого этапа.
Вероятность победы в этот этап не входит.

Проверки: `go test ./...` через установленный SDK Go 1.27.2, 75/75 тестов Node,
Edge 1440/768/390. Браузер получает ответы настоящих Go-мапперов, сгенерированные
из локальных GC/метаданных; соединение с рабочей PostgreSQL не проверялось.
Скрипт проверки и снимки: `.taste-skill/graph-fixture/`.

**Ограничение точности:** командные ряды и личный урон подключены в пробном
масштабе и помечены в `preliminary_series` значениями `team_net_worth`,
`team_experience`, `hero_damage`, если соответствующие ряды непустые.
Пока это не данные, сверенные с клиентом Dota. Интерфейс показывает предупреждение
и знак ≈ на оси и в подсказках. Контрольная сверка масштаба/времени остаётся открытой.

## Интерфейс

Отдельная вкладка «Графики» страницы матча, четыре режима:

1. Преимущество команд по общей ценности и опыту: Radiant минус Dire,
   положительные значения над нулём, отрицательные под нулём.
2. Общая ценность игроков: до десяти линий с постоянным цветом каждого игрока.
3. Уровни игроков: ступенчатые линии по событиям повышения уровня.
4. Накопленный урон игроков героям: до десяти линий.

Список игроков по командам позволяет включать и скрывать линии; доступны
выбор всей команды и сброс. Общий курсор времени показывает значения включённых
рядов с героями и никами. На телефоне выбор времени работает нажатием и ползунком.
Убийства героев показываются отметками по сторонам на шкале, с фильтрами
«Все / Radiant / Dire / выбранные игроки / скрыть» и подсказками участников.
Фильтр команды обозначает команду погибшего: верхняя полоса — смерти Radiant,
нижняя — смерти Dire. В подсказке это написано явно.

Для каждого значения подсказка использует последнюю точку не позже курсора
и показывает фактическое время этой точки. До первой точки — нет данных.
Визуальная линия соединяет образцы; это не означает точных данных на каждую
секунду. Уровни соединяются ступенями, без дробных значений.
Покупки и инвентарь остаются в своих существующих вкладках.

## Запрос

`GET /api/matches/{id}/graphs`, где `id` — внутренний ID матча.

Новый импорт, таблица БД или демка для этих четырёх режимов не нужны:
основной матч и исходный JSON метаданных уже хранятся в БД.
Ники, изображения героев, составы и победитель берутся из основного API матча.

## Ответ

Ниже только пример формы, числа условные. Он не является результатом
декодирования реальных командных графиков.

```json
{
  "match_id": "5",
  "dota_match_id": "9040846950",
  "duration": 2375,
  "available": true,
  "teams": [
    {
      "side": "radiant",
      "net_worth": [{"game_time": 0, "value": 3000}],
      "experience": [{"game_time": 0, "value": 0}]
    },
    {
      "side": "dire",
      "net_worth": [{"game_time": 0, "value": 3000}],
      "experience": [{"game_time": 0, "value": 0}]
    }
  ],
  "players": [
    {
      "player_slot": 0,
      "net_worth": [{"game_time": 0, "value": 590}],
      "hero_damage": null,
      "levels": [{"game_time": 0, "value": 1}, {"game_time": 147, "value": 2}]
    }
  ],
  "kills": [
    {
      "game_time": 440,
      "killer_player_slots": [128],
      "victim_player_slot": 0,
      "bounty": 307
    }
  ]
}
```

- Все ID матчей — строки. `player_slot` — числовой слот Dota, включая 128–132.
- `duration` — продолжительность в секундах из основного GC-матча.
- Точка: `game_time` — целые игровые секунды, `value` — конечное неотрицательное
  число в обычных единицах: золото, опыт, урон или целый уровень 1–30.
- `teams` и `players` всегда массивы. На одну сторону/слот — одна запись.
  Не добавлять команды 6–13 без игроков как дополнительные игровые стороны.
- Каждый ряд независим: `null` означает недоступный или ещё не проверенный ряд;
  `[]` — источник известен, но точек нет. Ноль — реальное значение.
- `kills: null` означает недоступные события; `kills: []` — известное отсутствие
  убийств героев. Доступность отметок не зависит от доступности графиков.
- `available` означает наличие хотя бы одного непустого проверенного ряда.
  Если доступны только уровни, остальные режимы показывают отсутствие данных.
  При отсутствии метаданных: `available: false`, `teams: []`, `players: []`,
  `kills: null`; ID и duration остаются из основного матча.
- `preliminary_series` — массив имён перечисленных выше непроверенных рядов;
  для отсутствующих рядов и при отсутствии метаданных — `[]`.
- Поля вероятности победы и выдуманные нули для недоступных рядов не добавлять.

## DTO для реализации пользователем

Рекомендуемое размещение: `internal/http/dto/graphs.go`.
Имена новых типов не конфликтуют с существующим `NetWorthPoint`.
`omitempty` для рядов не нужен: отсутствие данных должно передаваться как null.

```go
type GraphPoint struct {
    GameTime int32   `json:"game_time"`
    Value    float64 `json:"value"`
}

type TeamGraphs struct {
    Side       string       `json:"side"`
    NetWorth   []GraphPoint `json:"net_worth"`
    Experience []GraphPoint `json:"experience"`
}

type PlayerGraphs struct {
    PlayerSlot uint32       `json:"player_slot"`
    NetWorth   []GraphPoint `json:"net_worth"`
    HeroDamage []GraphPoint `json:"hero_damage"`
    Levels     []GraphPoint `json:"levels"`
}

type GraphKill struct {
    GameTime          int32    `json:"game_time"`
    KillerPlayerSlots []uint32 `json:"killer_player_slots"`
    VictimPlayerSlot   uint32   `json:"victim_player_slot"`
    Bounty             *int32  `json:"bounty"`
}

type GraphsResponse struct {
    PreliminarySeries []string `json:"preliminary_series"`
    MatchID     string         `json:"match_id"`
    DotaMatchID string         `json:"dota_match_id"`
    Duration    uint32         `json:"duration"`
    Available   bool           `json:"available"`
    Teams       []TeamGraphs   `json:"teams"`
    Players     []PlayerGraphs `json:"players"`
    Kills       []GraphKill    `json:"kills"`
}
```

При переносе событий из protobuf проверить фактические типы исходных полей,
не делать небезопасных приведений отрицательных значений к uint32.

## Правила маппинга

### Личная общая ценность

Источник `Team.Player.graphNetWorth`. Использовать тот же расчёт, что уже
используется в `inventory_mapper.go`: время `ceil(index * duration / count)`,
значение `floor(raw) * 10`. Первой точке соответствует index 0.
Это эмпирическая привязка, согласующаяся со сверкой двух матчей; универсальность
для всех версий метаданных не установлена. Не создавать второй отличающийся
расчёт для графиков и перемотки.

### Уровни

Источник `Team.Player.levelUpTimes`, не `abilityUpgrades`.
Базовая точка `{game_time: 0, value: 1}`; элемент массива с индексом 0 —
получение уровня 2, с индексом 1 — уровня 3 и так далее.
В файле 9040846950 это подтверждается всеми десятью итоговыми уровнями GC
и снимками инвентаря; у Techies уровень 2 получен на 147-й секунде.
Порядок исходного массива задаёт номер уровня: не сортировать времена отдельно
перед назначением уровней. Проверить неубывание, диапазон времени и предел 30.
Совпадающие секунды допустимы: несколько уровней могут быть получены подряд;
последний уровень в эту секунду является текущим. Не добавлять отсутствующие
повышения лишь ради совпадения с итоговым GC-уровнем.

### Командные опыт и общая ценность

Источники `Team.graphExperience` и `Team.graphNetWorth`.
Выбор стороны по `dotaTeam`: 2 — Radiant, 3 — Dire.
`graphGoldEarned` означает заработанное золото и не заменяет общую ценность.

В этом файле у каждой команды 64 значения каждого ряда. Масштаб и время точек
пока не подтверждены клиентом Dota. В реализованном предварительном режиме
используются время `ceil(index * duration / count)`, ОЦ `floor(raw) * 10`,
опыт `round(raw * 10)`, с обязательными отметками `preliminary_series`.
Это выбранная пробная нормализация, не результат подтверждённого декодирования.
После нормализации сервер отдаёт абсолютные значения обеих команд; фронтенд
вычисляет Radiant − Dire на объединении времён, выбирая последнее известное
значение каждой команды. До наличия обеих сторон преимущество неизвестно.

### Урон героям

Источник `Team.Player.graphHeroDamage`, накопленный показатель.
В файле по 39 точек у каждого игрока. Масштаб и ось времени требуют сверки.
Например, последняя сырая точка Techies — 2562.3218, итоговый урон GC — 26422.
Их несовпадение не доказывает коэффициент: последняя точка может предшествовать
финалу матча. В реализованном предварительном режиме: `round(raw * 10)` и
время `ceil(index * duration / count)`, с отметкой `hero_damage`.
Не растягивать значения к итоговому урону.

### Убийства героев

Источник `Team.kills`. В первой версии передавать только события убийства
героя: проверенный тип 0 и жертва, соответствующая слоту игрока основного матча.
Не смешивать с уничтожением объектов, Roshan/Miniboss и victim slot 255.
Команду события определять по участникам основного матча, а не по тому,
в массиве какой команды лежала запись.

Список убийц сохранить массивом; не выбирать первого, если участников несколько.
Неизвестный убийца (например, slot 255) не становится игроком: список известных
убийц может быть пуст. Не называть этих участников ассистентами — отдельного
списка ассистов здесь не установлено. Bounty сохранять при наличии, не путать
его с изменением net worth и не делить на число участников без основания.
Параллельные убийства в одну секунду сохранять отдельными записями.

## Проверки и ошибки

Повторить проверки ID и чтения БД из обработчика инвентаря: положительный
внутренний ID, 404 для отсутствующего матча, совпадение Dota ID GC и метаданных,
проверка публичной части. Неверный JSON/ID — ошибка сервера, не «данных нет».
Ошибки возвращаются через существующий `WriteError`.

Проверить точки на NaN/Infinity, отрицательные значения и выход за duration;
при наличии графиков duration должен быть положительным. Сортировка стабильная
по `game_time`; одинаковое время допустимо. Не выкидывать плохую сырую точку
до назначения времени, иначе сдвинется весь ряд.

Контрольные случаи: доступные уровни при null остальных рядов; только одна
команда; отсутствующие и пустые метаданные; неизвестный слот; повтор слота;
одновременные уровни/убийства; точка на 0 и на duration; отрицательное время
события до старта; невалидная длительность; несовпадение ID; ошибка БД.
Проверить совпадение личной ОЦ этого API и API инвентаря на одинаковом времени.
