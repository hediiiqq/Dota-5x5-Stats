## Конфигурация

Сайт и импортер используют один образ с двумя бинарниками. Go-код не изменён.
Для последующих обновлений сборку должен выполнять CI, а VPS — скачивать готовый образ. Контекст сборки ограничен
списком разрешённых исходников и публичных файлов в `.dockerignore`.

## Состав

- `web`: сайт, 256 МБ RAM; порт 8080 доступен только через localhost и Docker-сеть.
- `proxy`: Caddy, 128 МБ RAM; принимает 80/443, перенаправляет HTTP на HTTPS,
  выпускает и продлевает сертификаты. Данные ACME и сертификаты сохраняются
  в `caddy_data`, конфигурационное состояние — в `caddy_config`.
- `db`: PostgreSQL 18, 512 МБ RAM; порт БД наружу не опубликован.
- `importer`: разовый запуск существующего CLI, 512 МБ RAM.
- `postgres_data`: постоянные данные PostgreSQL.
- `steam_tokens`: токены импортера в `/state`, вне образа.

Планировщик запускает импорт через 5 минут после загрузки и через 30 минут
после завершения предыдущего запуска. `flock` исключает наложение импорта и
обновления. Пароли Steam не передаются контейнеру сайта.

## Первый запуск на VPS

Нужны Linux amd64, Docker Engine и Docker Compose 2.30+ (`env_file.format: raw`).
Конфигурация устанавливается в `/opt/dota-stats`, секреты — в `/etc/dota-stats`
с правами каталога 700 и файлов 600. Содержимое env-файлов передаётся буквально:
значения записывать без дополнительных кавычек. Не выполнять `docker compose
config` с выводом в публичные логи — он может раскрывать значения переменных.

Создать отдельно на сервере:

```text
/etc/dota-stats/db.env
  POSTGRES_DB=dota_stats
  POSTGRES_USER=dota_admin
  POSTGRES_PASSWORD=<новый случайный пароль>

/etc/dota-stats/web.env
  DB_URL=postgres://<read-only-user>:<url-encoded-password>@db:5432/dota_stats?sslmode=disable&pool_max_conns=5
  STEAM_WEB_API_KEY=<необязательный ключ>

/etc/dota-stats/importer.env
  DB_URL=postgres://dota_admin:<url-encoded-password>@db:5432/dota_stats?sslmode=disable&pool_max_conns=5
  ACCOUNT1_USERNAME=<логин>
  ACCOUNT1_PASSWORD=<пароль>
  ACCOUNT2_USERNAME=<логин>
  ACCOUNT2_PASSWORD=<пароль>

/etc/dota-stats/release.env
  DOTA_IMAGE=ghcr.io/<owner>/<repository>:sha-<commit>
```

Заполнители заменяются реальными значениями только на VPS, не в этом файле.
Пользователь чтения для сайта создаётся после инициализации БД с правами
`CONNECT`, `USAGE ON SCHEMA public` и `SELECT` на таблицы матчей. На VPS
подключение `sslmode=disable` ограничено локальной Docker-сетью; это не совет
отключать TLS при подключении к удалённой БД.

```sh
cd /opt/dota-stats
docker compose --env-file /etc/dota-stats/release.env up -d --wait db web proxy
```

Четыре начальные миграции выполняются PostgreSQL только при создании пустого volume.
Они не применяются заново к существующей БД. Начиная с 005, миграции выполняет
`deploy/migrate.sh`: при обновлении `deploy/update.sh` сначала дожидается готовности
БД, применяет миграции и права, а затем переключает образ сайта.

## Авторизация: первый деплой

До отправки версии с авторизацией добавьте в `/etc/dota-stats/web.env`,
сохранив существующие `DB_URL`, API-ключи и остальные настройки:

```dotenv
PUBLIC_BASE_URL=https://dota-stats5x5.duckdns.org
ADMIN_STEAM_IDS=<разрешённые SteamID64 через запятую>
ADMIN_CSRF_SECRET=<base64 от 32 случайных байт>
```

Секрет можно один раз создать командой `openssl rand -base64 32` и сохранить
в этом файле без кавычек. Не менять его при каждом деплое и не коммитить env-файл.
Файл остаётся на VPS; workflow не переносит локальный `.env`.
Пустой список администраторов запрещает доступ. Срок сессии — 15 дней.

`deploy/migrate.sh` применяет файлы `migrations/NNN_*.up.sql` начиная с 005
в порядке номеров. Миграции 001–004 остаются существующей базовой схемой;
перед началом проверяется наличие их четырёх таблиц. Для 005 и выше в
`public.app_schema_migrations` сохраняются номер, имя файла, SHA-256 и время
применения. Повторное обновление пропускает выполненные файлы. Изменение
имени или содержимого применённой миграции останавливает деплой: для следующего
изменения схемы добавляйте новый номер. Переводы строк LF/CRLF нормализуются
при вычислении checksum.

По умолчанию роль сайта — `dota_web`, как в существующем размещении.
Она должна уже существовать и использоваться в `DB_URL` сайта. Скрипт выдаёт
ей USAGE на схему public и SELECT/INSERT/UPDATE/DELETE только на:

- `public.admin_sessions`;
- `public.admin_login_attempts`;
- `public.admin_openid_nonces`.

Скрипт не выдаёт права записи в таблицы матчей и не создаёт роль/пароль.
Для ручного запуска с другим именем роли можно передать переменную
`DOTA_WEB_DB_ROLE`. При автоматическом деплое используется `dota_web`,
если эта переменная не задана в окружении процесса обновления.

Весь пакет миграций, журнал и выдача прав выполняются в одной транзакции
под advisory lock PostgreSQL и существующей блокировкой релиза. Ошибка SQL,
отсутствующая роль или несовпадающий checksum откатывают транзакцию и прерывают
обновление до переключения образа. Новый web-контейнер в этой ветке не запускается.
Успешно выполненные миграции не откатываются при последующем неудачном запуске
нового приложения: изменения должны быть совместимы с прежней версией.
Файлы `.down.sql` при деплое не выполняются. Новые `.up.sql` должны допускать
выполнение внутри транзакции и не содержать собственных BEGIN/COMMIT.

Если таблицы 005/006 были созданы на VPS вручную без журнала миграций, первый
автоматический запуск остановится на существующих таблицах. Это не повод их
удалять: сначала нужно отдельно сверить схему и зарегистрировать уже выполненные
миграции в журнале. Автоматического признания произвольной схемы корректной нет.

Отдельный запуск на VPS (БД должна быть запущена):

```sh
cd /opt/dota-stats
sudo sh deploy/migrate.sh
```

Команда `sh deploy/migrate.sh --sql` только выводит SQL-пакет для проверки,
без подключения к БД. Шесть интеграционных проверок запускаются в CI на отдельном
PostgreSQL 18: первый/повторный запуск, сохранность сессий и ограниченные права,
откат при ошибке, несовпадающий checksum, отсутствующая роль, дубли номеров
и параллельные запуски. Сам VPS в этих проверках не используется.

При переносе data-only дампа в уже созданную схему учитывать порядок внешних
ключей: обычный `pg_restore --data-only` может попытаться загрузить метаданные
раньше матчей. Для первого восстановления в пустую БД использовались
`--disable-triggers --single-transaction` под администратором, затем проверены
количества строк и отсутствие записей без родительского матча.

Данные существующей локальной БД переносятся дампом отдельно: файл
`api-match.example.json` не является резервной копией PostgreSQL.
Первый запуск импортера выполнить вручную, проверить Steam Guard и доступность
матчей, затем включать таймер. Существующие токены можно перенести в volume,
назначив владельца `10001:10001` и права 600.

```sh
sh deploy/import.sh
cp deploy/dota-stats-import.service deploy/dota-stats-import.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now dota-stats-import.timer
```

CLI сейчас может завершаться с кодом 0 даже при ошибках отдельных аккаунтов;
успех systemd unit сам по себе не подтверждает загрузку новых матчей. Следить
за журналом импорта и временем последнего сохранённого матча.

## CI/CD

Workflow `.github/workflows/deploy.yml` проверяет Go и JS, собирает Linux amd64
образ, публикует его в GHCR с тегом коммита и обновляет VPS по SSH.
Для pull request выполняются только проверки. Запуск по push настроен на `master`.

Перед первым автоматическим обновлением в GitHub задать переменные:

- `VPS_HOST`, `VPS_USER`, при необходимости `VPS_PORT`;
- `DEPLOY_ENABLED=true` — только после успешного первого ручного запуска.

Секреты GitHub: `VPS_SSH_KEY` (отдельный ключ развёртывания),
`VPS_KNOWN_HOSTS` (проверенная запись host key сервера). Пароль root для CI не нужен.
Подготовленные значения находятся только в игнорируемом локальном каталоге:
`VPS_SSH_KEY` — содержимое `.local/deploy-private/github-actions-ed25519`,
`VPS_KNOWN_HOSTS` — содержимое `.local/deploy-private/github-actions-known-hosts`.
Эти файлы не коммитить. Для текущего сервера достаточно Variables
`VPS_HOST=157.228.187.252` и `DEPLOY_ENABLED=true`; пользователь root и порт 22
выбираются workflow по умолчанию.
Пользователь SSH должен иметь право на Docker и каталог `/opt/dota-stats`.
Права Docker фактически дают административный доступ к хосту.

Обновление проверяет health контейнеров, валидирует и перезагружает Caddy,
проверяет запрос к БД через `/api/matches` внутри web и через доверенное
публичное HTTPS-соединение. Перезагрузка Caddy нужна даже при изменении только
содержимого bind-mounted файлов. Изменение конфигурации и образа сериализовано
общей блокировкой в `deploy/apply.sh`.
При неуспехе возвращается прежний тег образа; данные БД и токены не удаляются.
Это откат приложения, а не миграций или конфигурации. После deploy токен входа в
GHCR, выданный текущему workflow, истечёт; следующий workflow авторизует сервер
заново. Для ручных pull приватного образа нужна отдельная авторизация GHCR.

## Перед открытием доступа

- Текущий API не требует авторизации: история и Account ID будут доступны посетителям.
- HTTPS уже включён на IP. Для ограничения доступа к истории нужна отдельная
  авторизация; шифрование само по себе не ограничивает круг посетителей.
- Хранить резервные копии вне VPS; Docker volume не является резервной копией.
- На диске 15 ГБ контролировать место, ограничивать логи и удалять только
  заведомо ненужные образы. Не запускать `docker compose down -v`: это удалит БД
  и токены.

Описание параметров env_file: https://docs.docker.com/reference/compose-file/services/#env_file
Путь volume PostgreSQL 18: https://hub.docker.com/_/postgres

## HTTPS и бесплатное имя

Домен `dota-stats5x5.duckdns.org` указывает на `157.228.187.252` и подключён
через `deploy/caddy-domains/dota-stats5x5.caddy`. Для него Caddy выпускает
отдельный публичный сертификат и автоматически продлевает его. Конфигурация
сохранена и на VPS, и в рабочей копии проекта. Токен DuckDNS серверу не передавался.

`deploy/Caddyfile` использует Let's Encrypt ACME с профилем `shortlived` для IP
157.228.187.252. Сертификат проверен извне с системным хранилищем доверия;
первый выдан до 30 октября 2026, 04:57:01 UTC. Продление автоматическое, пока
proxy работает, volume `caddy_data` сохранён и сервер доступен на 80/443.
Короткие IP-сертификаты действуют 160 часов. Не удалять volume с данными Caddy.

`default_sni` направляет подключения без SNI на сертификат публичного IP:
браузеры не передают SNI для IP-адреса, а контейнер видит собственный внутренний IP.

Бесплатное имя можно получить в виде поддомена:

- [DuckDNS](https://www.duckdns.org/about.jsp): `имя.duckdns.org`, рекомендуемый вариант.
- [FreeDNS](https://freedns.afraid.org/): выбор поддоменов в общем каталоге.

Для DuckDNS пользователь входит в собственный аккаунт, создаёт доступное имя
и устанавливает IPv4 `157.228.187.252`. Пока IP VPS не меняется, динамическое
обновление адреса не нужно. Токен аккаунта не нужен для HTTP/TLS-проверки Let's
Encrypt и не должен попадать в образ, репозиторий или Caddyfile.

После создания имени добавить на сервере `deploy/caddy-domains/site.caddy`:

```caddyfile
выбранное-имя.duckdns.org {
    reverse_proxy web:8080
}
```

Вместо заполнителя использовать фактически зарегистрированное имя.
Сначала проверить, что DNS A-запись возвращает IP VPS, затем:

```sh
cd /opt/dota-stats
docker compose --env-file /etc/dota-stats/release.env exec -T proxy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
docker compose --env-file /etc/dota-stats/release.env exec -T proxy caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile
```

Для доменного блока Caddy использует обычный профиль публичного сертификата;
`shortlived` задан только для IP. Файл домена также сохранить в локальном
репозитории, чтобы конфигурация была воспроизводимой.

Источники: [IP-сертификаты Let's Encrypt](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability),
[автоматический HTTPS Caddy](https://caddyserver.com/docs/automatic-https).
