# API Dota Stats — контракт локальной версии

Основа: предоставленный ответ координатора для матча `9034163193`. Один пример подтверждает наличие полей в этом ответе, но не гарантирует их наличие во всех матчах.

Документ описывает целевой формат нашего HTTP API. `../main.go` реализует перечисленные поля игроков и вложенные массивы для локального импорта. По решению владельца чтение, преобразование и обработчики оставлены внутри `main()`. Ошибки пока возвращаются текстом через `http.Error`; JSON-формат ошибок ниже остаётся целевым. Данные хранятся в памяти и читаются из `testdata/match.json` при запуске. Подключение Steam/координатора, PostgreSQL и загрузка демок ещё не реализованы.

Согласованный состав статистики игрока: все поля из `../testdata/match.json`, кроме `activePlusSubscription`, `heroWasRandomed`, `heroWasDotaPlusSuggestion` и `mmrType`. Эти четыре поля остаются в исходном JSON, но не входят в наш HTTP API. На один исходный объект игрока приходится один объект MatchPlayer: 48 перенесённых полей и производное поле `side`.

Связанные документы: [план](PROJECT_PLAN.md), [структура](PROJECT_STRUCTURE.md), [навигация по этапам](PROJECT_GUIDE.md).

## Общие правила

- Ответы описанных маршрутов, включая ошибки, имеют `Content-Type: application/json`.
- Имена JSON-полей — в `snake_case`, например `dota_match_id`.
- Внешние идентификаторы матча и аккаунта передаются строками. Наш внутренний `id` пока является положительным целым числом.
- Время начала — строка RFC 3339 в UTC; длительность — целое число секунд.
- Неизвестное значение передаётся как `null`, известный ноль — как `0`. При импорте нужно сохранять различие между отсутствующим полем и явно переданным нулём.
- Известный пустой список — `[]`; отсутствующий в источнике массив статистики — `null`. Для списка матчей и списка игроков используем массивы, в том числе пустые.
- Числовые коды, флаги и показатели с неподтверждённым смыслом сохраняются без догадок. Ноль в источнике переносится как ноль, но сам по себе не доказывает достоверность показателя.
- Поле `result` исходного ответа относится к запросу координатора, а не к победителю матча. Его обработку требуется сверить со схемой используемой библиотеки; в публичный ответ матча оно не входит.

Сейчас проверяются чтение файла, корректность JSON, наличие объекта `match` и десяти игроков. Необязательные показатели могут отсутствовать. Проверка `result` пока не реализована; перед подключением живого координатора требуется подтвердить смысл его кодов.

## Запуск

Из корня проекта: `go run .`. Сервер слушает порт `8080`. Проверка кода: `go build .` и `go vet ./...`; ответы API проверяем вручную.

Проверка ответа: открыть `http://localhost:8080/api/matches/1`. Полный пример сформирован из нашей модели: [docs/api-match.example.json](api-match.example.json).

## Маршруты первого этапа API

| Метод и путь | Назначение | Успех |
| --- | --- | --- |
| `GET /api/health` | Проверка, что HTTP-сервер отвечает | `200`, объект со статусом |
| `GET /api/matches` | Список добавленных матчей | `200`, массив объектов Match |
| `GET /api/matches/{id}` | Один матч по внутреннему ID нашей базы | `200`, объект Match |

В первой учебной версии список возвращает полные объекты Match без фильтров и пагинации. Пока источником служит локальный `../testdata/match.json`; подключение координатора и хранилища — следующие этапы. Запросы пока не требуют авторизации; доступ группы добавляется на этапе 8 плана.

### GET /api/health

```json
{"status":"ok"}
```

Проверяет доступность HTTP-сервера. Проверка PostgreSQL пока не предусмотрена.

### GET /api/matches/{id}

`id` в адресе — наш внутренний ID, например `/api/matches/1`. Это не внешний ID Dota `9034163193`.

- `400` — ID не является положительным целым числом допустимого диапазона.
- `404` — ID корректен, но такого матча нет в нашем хранилище.
- `500` — внутренняя ошибка сервера.

## Объект Match

Все перечисленные ключи присутствуют в ответе. Пометка `null` означает, что значение может быть неизвестно.

| Поле нашего API | Тип JSON | Источник и смысл |
| --- | --- | --- |
| `id` | integer | Внутренний ID, назначенный нашим приложением; в исходном JSON его нет |
| `dota_match_id` | string или null | `match.matchId`; в примере `"9034163193"` |
| `started_at` | string или null | `match.starttime`, преобразованный из Unix-времени в секундах в UTC |
| `duration` | integer или null | `match.duration`; в примере `1998` секунд, то есть 33:18 |
| `game_mode` | integer или null | Исходный `gameMode`; код режима игры. Доступно в `cmd/server` |
| `game_mode_name` | string или null | Название известного режима по константам GC, например `Captains Mode` (2), `Captains Draft` (16), `Turbo` (23); неизвестный или отсутствующий код даёт `null`. Доступно в `cmd/server` |
| `picks_bans` | array | Записи `picksBans` в исходном порядке: `is_pick` (boolean или null), `team` (integer или null; 0 — Radiant, 1 — Dire), `hero_id` (integer или null), `hero_name` и `hero_icon_url` (string или null). Неизвестный герой сохраняет ID; отсутствующие записи возвращаются как `[]`. Доступно в `cmd/server` |
| `winner` | string или null | `"radiant"`, `"dire"` либо `null`; преобразование `matchOutcome` нужно подтвердить по protobuf-схеме |
| `players` | array of MatchPlayer | `match.players`; в предоставленном примере десять игроков |

В примере `starttime: 1791407595` соответствует `2026-10-07T21:13:15Z`. Дата в имени исходного файла не используется как время начала матча.

Исходное значение результата — `matchOutcome: 2`. До проверки его смысла `winner` остаётся `null`. Счёт `43:20`, состояние башен и число убийств не используются для определения победителя.

### DamageBreakdown

Одинаковый формат элементов `hero_damage_received` и `hero_damage_dealt`:

| Поле нашего API | Тип JSON | Источник |
| --- | --- | --- |
| `pre_reduction` | number или null | `preReduction`; исходное значение урона до уменьшения |

В примере `heroDamageDealt` заполнен нулями, хотя `heroDamage` ненулевой. Массив всё равно входит в API и сохраняется без изменений значений; до проверки источника не используем его для вычисления распределения нанесённого урона.

### Производные поля и идентификаторы

Предлагаемое правило сторон: `teamNumber: 0` → `radiant`, `teamNumber: 1` → `dire`. В этом примере этим группам соответствуют `playerSlot` 0–4 и 128–132. Правило нужно подтвердить по схеме/игровому экрану при подключении координатора. Неизвестный код или противоречивые данные не превращаются автоматически в одну из сторон.

SteamID64 не добавляем: в предоставленном JSON нет отдельного поля с таким идентификатором. Если он понадобится, преобразование реализуется и документируется отдельно. Ник не используется как ключ объединения игроков.

## Формат ошибок

Предлагаемый единый ответ:

```json
{
  "error": {
    "code": "match_not_found",
    "message": "Матч не найден"
  }
}
```

| HTTP-код | `error.code` | Когда возвращается |
| --- | --- | --- |
| `400` | `invalid_match_id` | Неверный формат или диапазон ID |
| `404` | `match_not_found` | Матч с корректным ID отсутствует |
| `500` | `internal_error` | Внутренняя ошибка; подробности записываются в серверный лог |
| `404` | `not_found` | Неизвестный маршрут |
| `405` | `method_not_allowed` | Неподдерживаемый метод известного маршрута; заголовок `Allow: GET, HEAD` |

Таблица и JSON-пример выше описывают целевой формат ошибок. Текущие обработчики возвращают `400` при ошибке `strconv.Atoi` и `404`, если ID не совпадает с ID загруженного матча, через текстовый `http.Error`. Неизвестные маршруты и методы обрабатывает стандартный маршрутизатор. Проверка положительного ID и единые JSON-ошибки пока не реализованы. Ошибки кодирования ответа записываются в лог без дописывания второго ответа.

## Данные матча для дальнейшего расширения

У матча в исходном примере также присутствуют режим, тип лобби, число людей, счёт сторон, время первой крови, пики и баны, состояние башен и бараков, сведения о команде Radiant и демке. Их добавление в объект Match согласуется отдельно. Договорённость «все поля, кроме четырёх» относится к данным игроков.

Исходный `../testdata/match.json` сохраняем целиком, включая четыре исключённых из API поля игроков. HTTP-контракт задаёт преобразование данных, а не удаление полей из исходного ответа. Новые, пока не описанные поля источника не включаются в HTTP API автоматически: сначала дополняем этот документ.

## Реализация и проверка

- Чтение файла, преобразование игроков и регистрация трёх маршрутов находятся внутри `main()`. Метод `Match.Validate()` проверяет количество игроков. Дополнительные функции преобразования и HTTP-обёртки удалены по решению владельца.
- Исходные структуры имеют теги координатора; выходные структуры — теги этого контракта. Неизвестные значения не заменяются нулями.
- ID матча и группы читаются как 64-битные беззнаковые числа, AccountID — как 32-битное беззнаковое число. Все внешние ID в HTTP-ответе — строки.
- Время начала приводится к UTC. Отдельная проверка диапазона даты пока не реализована.
- Маршруты регистрируются через `http.HandleFunc`; ID читается через `strconv.Atoi`. Чужой корректный ID возвращает `404`.
- По решению владельца проекта автоматические тесты удалены. При изменениях проверяем сборку и ответы API вручную.

Следующий этап: проверить живой координатор отдельно от HTTP API и подтвердить коды `matchOutcome`, правила команд и смысл неоднозначных показателей. До этого `winner` остаётся `null`. База данных и повторный импорт — отдельные следующие задачи.
