# API перемотки инвентаря

Статус: DTO, маппер, обработчик и маршрут реализованы пользователем.
Пользователь подтвердил получение и сверку данных на запущенном API.
Автоматические тесты бэкенда и все ошибочные HTTP-сценарии пока не подтверждены.
Интерфейс подключён в отдельной вкладке «Инвентарь»; проверен тестами Node и
в Edge на 1440/768/390px на локальной фикстуре из исходных метаданных.

## Маршрут и способ загрузки

Реализован `GET /api/matches/{id}/inventory`, где `id` — внутренний ID БД,
как у существующего маршрута покупок. Один ответ содержит все доступные
снимки всех игроков матча. Выбор одного игрока любой стороны или пары
Radiant + Dire и общая перемотка выполняются на JavaScript.

Отдельный маршрут сохраняет текущий контракт покупок. Альтернатива — выдавать
снимок на запрошенную секунду, но это потребует сетевых запросов при перемотке
и переключении игроков. Для текущего файла с 820 снимками предлагается
загрузка целиком; объём ответа проверяется при подключении реального API.

## Пример ответа

ID БД условный; показан только первый снимок игрока слота 0 из локального
файла матча 9040846950. Реальный ответ содержит всех доступных игроков и снимки.

```json
{
  "match_id": "123",
  "dota_match_id": "9040846950",
  "available": true,
  "players": [
    {
      "player_slot": 0,
      "snapshots": [
        {
          "game_time": -60,
          "item_ids": [44, 34, 43, 16, 237, 1123],
          "backpack_item_ids": [16],
          "neutral_item_id": null,
          "neutral_enhancement_id": null,
          "kills": 0,
          "deaths": 0,
          "assists": 0,
          "level": 1,
          "last_hits": 0,
          "denies": 0,
          "flags": 0
        }
      ]
    }
  ]
}
```

## Правила маппинга

- Оба ID матча — строки. Сверять Dota match ID метаданных с основным
  сохранённым матчем, чтобы не выдать данные другого матча.
- Источник: `CDOTAMatchMetadataFile.metadata.teams[].players[].inventorySnapshot`.
  Слоты должны быть уникальными и соответствовать игрокам основного ответа
  матча. Герой, ник, аватар и сторона берутся из основного API.
- `game_time` — обязательное целое знаковое число секунд относительно начала
  игры. Отрицательные значения допустимы. Использовать фактические времена,
  не создавать снимки с условным шагом 30 секунд. Сортировать по возрастанию;
  при одинаковом времени сохранять исходный порядок.
- `item_ids` и `backpack_item_ids` — списки ID из `itemId` и `backpackItemId`.
  Отсутствующее repeated-поле нормализовать в `[]` — записанных предметов нет.
  Сохранять порядок, повторы и исходные значения. Не дополнять массивы до
  шести/трёх ячеек на сервере и не объявлять индекс точным номером слота:
  это соответствие ещё не подтверждено. Неизвестный положительный ID допустим.
- Варды, TP и рецепты не фильтровать. Фильтр таблицы покупок к снимкам не относится.
- `neutral_item_id`, `neutral_enhancement_id`: отсутствующее поле — `null`;
  присутствующее значение сохранять, включая протокольное `-1`.
  В интерфейсе положительное значение означает предмет, неположительное —
  отсутствие предмета; `null` означает отсутствие сведений.
- `kills`, `deaths`, `assists`, `level`, `last_hits`, `denies`, `flags`:
  число при наличии поля, иначе `null`. Не применять `omitempty` к этим
  полям ответа: известный ноль должен оставаться нулём. Проверять указатели
  исходных optional-полей; геттеры могут скрывать отсутствие данных.
- `flags` передавать без потери неизвестных битов. Известные биты: 1 — Scepter,
  2 — Shard. Наличие предмета также проверяется по соответствующему снимку;
  итоговые `permanent_buffs` нельзя переносить на всё время матча.
- Отсутствие обязательного времени, повтор слота или несоответствие ID —
  ошибка сохранённых данных (5xx), а не успешный пустой ответ.

## Доступность и ошибки

- Матч есть, метаданных либо записей снимков нет: HTTP 200,
  `available=false`, `players=[]`, корректные ID из основного матча.
- `available=true` означает наличие хотя бы одного снимка; полнота по всем
  игрокам этим не гарантируется. Игрок без записанных снимков может иметь
  `snapshots=[]` или отсутствовать в `players`; интерфейс показывает
  «Нет снимков игрока», а не пустой инвентарь.
- Неверный внутренний ID: 400; матч не найден: 404; ошибка БД или повреждённый
  JSON/структура: 500. Формат ошибок — существующий `WriteError`.
- Для неподдерживаемого метода — 405 и существующий заголовок `Allow`.
- HTTP-обработчик только читает БД, без загрузки файла с Valve.

## Использование в интерфейсе

Для выбранного времени брать последний снимок с `game_time <= время`.
При одинаковом времени использовать последний в исходном порядке.
До первого снимка показывать отсутствие данных. После последнего оставлять
последний доступный снимок с подписью его фактического времени, не объявляя
его итоговым. Не интерполировать предметы и K/D/A между снимками.
Для пары игроков время общее, ближайший доступный снимок определяется отдельно
для каждого. Смена игрока не сбрасывает выбранное время.

Оценки стиля игры в этот ответ не входят. Покупки не используются для
восстановления состояния инвентаря.

## Обязательное расширение: общая ценность по времени

По требованию пользователя `graphNetWorth` нужно подключить к этой же
перемотке. В исходном JSON есть два разных поля: личное
`metadata.teams[].players[].graphNetWorth` (39 точек у каждого из 10 игроков)
и командное `metadata.teams[].graphNetWorth` (64 точки у каждой активной
команды). Для карточки выбранного игрока использовать личный ряд.

Текущий Go DTO это поле ещё не отдаёт. Фронтенд уже поддерживает следующее
необязательное поле в каждой записи `players[]`:

```json
{
  "player_slot": 0,
  "snapshots": [],
  "net_worth": [
    { "game_time": 0, "value": 600 },
    { "game_time": 60, "value": 1200 }
  ]
}
```

Значения в примере условные и показывают формат; это не декодирование
реального `graphNetWorth` матча 9040846950.

- `game_time` — фактическая проверенная привязка точки к игровым секундам.
- `value` — конечное неотрицательное число в обычных единицах золота,
  приведённое сервером к проверенному масштабу. Фронтенд только округляет его
  для отображения, не применяя скрытых множителей.
- Ряд необязательный: отсутствует, `null` или `[]` — нет данных ОЦ по времени.
  Старый ответ API остаётся рабочим и продолжает показывать инвентарь.
- Сортировка стабильная по времени. Для выбранного времени берётся последняя
  точка не позже него; при одинаковом времени последняя из исходного порядка.
  Под числом показывается собственное время точки ОЦ, которое может отличаться
  от времени снимка инвентаря. До первой точки — «—», после последней —
  последняя величина с явной подписью. Итоговый `net_worth` GC не используется
  вместо истории.

Пользователь предоставил четыре снимка клиента Dota для Techies (слот 0)
матча 9040846950. Эмпирически подтверждено соответствие отображению:
`game_time = (index + 1) * 60`, `value = floor(raw_value) * 10`.

| Время на скриншоте | Индекс | Время точки | Исходное значение | ОЦ по формуле | ОЦ клиента |
| --- | --- | --- | --- | --- | --- |
| 1:00 | 0 | 1:00 | 59.6 | 590 | 590 |
| 10:02 | 9 | 10:00 | 183.70157 | 1830 | 1830 |
| 20:08 | 19 | 20:00 | 459.5281 | 4590 | 4590 |
| 39:05 | 38 | 39:00 | 998.203 | 9980 | 9980 |

Это значения для отображения по ряду метаданных с шагом в 10 золота,
а не восстановленный точный net worth на каждую секунду. На четырёх точках
простое округление `raw_value * 10` дало бы другие числа. До первой точки
(1:00) ряд не даёт ОЦ; предыгровые −90 секунд к нему автоматически не добавлять
и не вычитать. Время последней точки — 39:00, а не окончание матча.
Итоговая ОЦ GC (10070 для Techies) остаётся отдельным показателем.

Правило проверено для этого матча и этих четырёх моментов; перед заявлением
универсальности для всех версий метаданных сверить другие матчи и игроков.

Повторная проверка пользователем на матче **9051746426**, момент **30:01**,
обнаружила расхождение: Winter Wyvern — сайт 4380, Dota 4090; Earth Spirit —
сайт 11470, Dota 11240. Инвентарь, уровень, K/D/A и LH/DN на скриншотах
совпадают. Формула времени `(index + 1) * 60` и преобразование значения вместе
пока не прошли проверку на втором матче. Причина расхождения не установлена;
нужно сопоставить исходные и соседние точки обоих игроков, их количество и
длительность матча (61:26). Не исправлять это произвольным общим смещением
или коэффициентом. Исходных метаданных второго матча в рабочем каталоге пока нет.

Сама [схема protobuf](https://raw.githubusercontent.com/SteamTracking/Protobufs/master/dota2/dota_match_metadata.proto)
описывает массив `float`, но не документирует масштаб и шаг. При преобразовании
отклонять отрицательные и нечисловые значения (NaN/Infinity), не терять индексы
пропуском некорректных точек и не подставлять вместо них ноль.

DTO и заполнение ряда в маппере добавлены пользователем. Следующая задача —
уточнить преобразование по двум матчам и закрепить его контрольными тестами.
Новая таблица, миграция или маршрут для этого расширения не требуются.

## Последовательность реализации бэкенда

1. Добавить DTO снимка, снимков игрока и ответа, например в
   `internal/http/dto/inventory.go`; для optional-чисел использовать указатели.
2. Добавить чистый маппер из protobuf с валидацией и тестами. Существующий
   маппер покупок оставить с прежним контрактом.
3. Добавить обработчик по образцу `GetMetadata`: получить основной матч,
   прочитать JSON через `postgres.GetMetadata`, проверить ID и структуру,
   сформировать ответ. Новая таблица или миграция не требуется.
4. Зарегистрировать GET и обработчик неподдерживаемых методов в
   `internal/http/router.go`.
5. Проверить тестами корректный ответ, отсутствие метаданных/снимков,
   неизвестный матч, неверный ID, повреждённый JSON, несовпадение ID,
   отсутствие optional-полей, нули, отрицательное время, повторы предметов,
   неизвестные предметы, сортировку и сохранение вардов/TP/рецептов.

Контрольный файл: 10 игроков, 820 снимков, по 82 на игрока; первый момент
−60, последний 2370. У слота 0 первый инвентарь и рюкзак приведены в примере;
в последнем снимке нейтральный предмет 1638, улучшение 1593.

После реализации: `go test ./...`, затем проверка ответа реального API
против исходного JSON. Проверку с БД выполнять отдельно от чистых тестов маппера.
