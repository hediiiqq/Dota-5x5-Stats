# Dota Stats

Учебный проект на Go для статистики приватных матчей Dota 2 своей компании. Импортер получает матчи через Steam и Dota 2 Game Coordinator, сохраняет их в PostgreSQL, а веб-интерфейс показывает историю, подробности игр и общую аналитику. Для просмотра сохранённых матчей вход в Steam не требуется.

> **Фронтенд проекта разрабатывается нейросетью: HTML, CSS, JavaScript, интерфейс, графики и клиентские проверки в `web/`. Бэкенд на Go, импорт, БД и HTTP API развивает автор проекта.**

## Возможности

### История и статистика

- История матчей с датой, режимом, составами, героями, победителем и длительностью.
- Выбор 5, 10, 15, 20, 50 или 100 матчей на странице; по умолчанию 5. Настройка сохраняется в браузере и URL, возврат из матча восстанавливает страницу и её размер.
- Общая статистика популярных героев и банов.
- Статистика игрока: герои, победы, поражения, винрейт и популярные предметы; по нажатию на героя открываются матчи игрока на нём.
- Лучшие союзники: совместные игры, результаты и винрейт с фильтром минимального числа матчей.
- Поиск игроков по нику и Dota ID, аватарки, составная сортировка статистических таблиц.
- Сравнение двух игроков за выбранный период и на одном герое, личные противостояния, рекорды компании, итоги игрового дня с календарём и результаты по длительности матчей.
- Избранные матчи и заметки — локально в текущем браузере.

### Страница матча

- Обзор с сортируемыми таблицами Radiant/Dire, итогами команд, K/D/A, уровнем, общей ценностью, добиваниями, GPM/XPM, уроном и лечением.
- Итоговые предметы, рюкзак, нейтральные предметы, индикаторы Scepter/Shard, пики и баны. Переход в Steam-профиль игрока по аватарке.
- Покупки всех игроков по времени, включая время до начала игры. Варды, TP и рецепты скрыты только в таблице покупок.
- Перемотка инвентаря: один игрок любой стороны или пара Radiant/Dire, общая шкала времени, фактическое время снимка, предметы, уровень, K/D/A, LH/DN и личная общая ценность. Фильтр покупок к снимкам не применяется.
- Прокачка способностей и талантов. Шаги изучения и уровни доступности талантов не выдаются за подтверждённые уровни фактического изучения.
- Графики преимущества команд по ОЦ/опыту, личной ОЦ, уровней и накопленного урона героям; выбор линий, курсор времени и отметки смертей с фильтрами.
- Вкладка «Рекорды»: лидеры матча по основным показателям, включая всех игроков при равенстве значений.

Покупки, снимки инвентаря и графики требуют отдельно загруженных метаданных. Командные ряды ОЦ/XP и личный урон пока предварительные: интерфейс отмечает их знаком ≈; масштаб и временную ось ещё нужно сверить с клиентом Dota. Отсутствующие данные не заменяются нулями, неизвестные герои и предметы сохраняют подпись с ID. Даты показываются в часовом поясе браузера.

### Балансировщик команд

- Список друзей по Dota ID или ссылке OpenDota; также можно выбрать игрока из сохранённых матчей.
- Выбор десятерых участников и одной или нескольких допустимых позиций для каждого.
- Подбор двух пятёрок с позициями 1–5 и минимальной разницей среднего примерного MMR; альтернативные варианты и ручные перестановки с проверкой позиций.
- Оценка MMR по доступному рангу со звёздами. Для Титана можно временно указать MMR вручную; без него используется явно обозначенная условная нижняя граница.
- Обновление профилей через сервер: OpenDota, при временном отказе — STRATZ, если настроен токен. Устаревшие ранги обновляются перед расчётом; ошибка обновления блокирует расчёт по ним.

Друзья и позиции сохраняются в этом браузере. MMR не сохраняется в постоянное хранилище; ручное значение действует в текущей вкладке. При неизвестном ранге расчёт для игрока недоступен.

## Требования

- Go 1.27 или новее — версия указана в `go.mod`.
- PostgreSQL и созданная база данных; Docker Compose использует PostgreSQL 18.
- SQL-консоль GoLand, pgAdmin или `psql` для миграций при локальном запуске.
- Для импорта — настроенные Steam-аккаунты, Steam Guard и доступ к сети Steam. Сейчас конфигурация содержит два аккаунта.
- Node.js для тестов фронтенда; в CI используется Node.js 24. Для работы сайта Node.js и npm не требуются.

Все локальные команды ниже выполняются из корня репозитория.

## Настройка

```sh
go mod download
```

Скопируйте `.env.example` в `.env`. В PowerShell:

```powershell
Copy-Item .env.example .env
```

Если `.env` уже существует, отредактируйте его, сохранив текущие настройки.

| Переменная | Назначение |
| --- | --- |
| `DB_URL` | Подключение к PostgreSQL; требуется HTTP-серверу и импортерам |
| `STEAM_WEB_API_KEY` | Необязательный серверный Steam Web API key для аватарок |
| `STRATZ_TOKEN` | Необязательный серверный токен резервного источника профилей для балансировщика |
| `ACCOUNT1_USERNAME`, `ACCOUNT1_PASSWORD` | Первый Steam-аккаунт импортера |
| `ACCOUNT2_USERNAME`, `ACCOUNT2_PASSWORD` | Второй Steam-аккаунт импортера |

Пример `DB_URL`: `postgres://USER:PASSWORD@HOST:5432/DATABASE?sslmode=disable`. Замените заполнители своими значениями; специальные символы логина и пароля нужно кодировать для URL. Для удалённой БД используйте параметры TLS её администратора.

Конфигурация читает `.env`; переменные окружения процесса имеют приоритет. Для запуска только HTTP-сервера достаточно `DB_URL`. Ключи Steam/STRATZ используются сервером и не передаются браузеру. После изменения переменных перезапустите соответствующий процесс.

`.env`, `ACCOUNT1_TOKEN.txt` и `ACCOUNT2_TOKEN.txt` исключены через `.gitignore`.

### Миграции PostgreSQL

Для новой базы выполните миграции по порядку:

| Файл | Назначение |
| --- | --- |
| `migrations/001_initial.up.sql` | Матчи и исходные данные в JSONB |
| `migrations/002_initial.up.sql` | Участники матчей |
| `migrations/003_initial.up.sql` | Прогресс синхронизации аккаунтов |
| `migrations/004_match_metadata.up.sql` | Метаданные матчей |

Пример для `psql` — замените `HOST`, `USER` и `DATABASE`, пароль вводится по запросу:

```sh
psql -h HOST -U USER -d DATABASE -W -v ON_ERROR_STOP=1 -1 -f migrations/001_initial.up.sql
psql -h HOST -U USER -d DATABASE -W -v ON_ERROR_STOP=1 -1 -f migrations/002_initial.up.sql
psql -h HOST -U USER -d DATABASE -W -v ON_ERROR_STOP=1 -1 -f migrations/003_initial.up.sql
psql -h HOST -U USER -d DATABASE -W -v ON_ERROR_STOP=1 -1 -f migrations/004_match_metadata.up.sql
```

При локальном запуске приложение не применяет миграции автоматически и не ведёт таблицу их версий. Для существующей базы применяйте только ещё не выполненные миграции. Файлы `*.down.sql` удаляют соответствующие таблицы и данные.

## Запуск сайта

```sh
go run ./cmd/server
```

Сервер слушает `:8080` на всех сетевых интерфейсах. HTML, CSS и JavaScript раздаются этим же Go-сервером; отдельная сборка фронтенда не нужна. Запускайте сервер из корня, чтобы был доступен каталог `web/`.

| Раздел | Адрес |
| --- | --- |
| История матчей | [localhost:8080](http://localhost:8080/) |
| Общая статистика | `/?view=stats` |
| Игроки | `/?view=player` |
| Союзники | `/?view=allies` |
| Аналитика | `/?view=insights` |
| Балансировщик | `/?view=balancer` |

Статистика загружает сохранённые матчи страницами через API. После импорта новых игр обновите статистику: API пока не предоставляет снимок базы для всей выборки.

## Импорт матчей из Steam

Заполните `DB_URL` и переменные обоих аккаунтов, примените миграции:

```sh
go run ./cmd/gc-check
```

При первом входе подтвердите авторизацию в мобильном приложении Steam. Токены сохраняются в `ACCOUNT1_TOKEN.txt` и `ACCOUNT2_TOKEN.txt` для следующих запусков. Таймаут работы каждого аккаунта — 15 минут, авторизации — 180 секунд.

Аккаунты обрабатываются параллельно. Импортер выбирает приватные лобби с `lobby_type=1` и режимами `game_mode=2` или `16`, получает подробности и сохраняет матчи с десятью участниками. Матч и участники записываются одной транзакцией; повторная запись Dota Match ID не создаёт дубль.

По умолчанию нижняя граница Dota Match ID — `6000000000`; при следующих запусках используется сохранённый прогресс каждого аккаунта.

```sh
go run ./cmd/gc-check -min-match-id=8000000000
go run ./cmd/gc-check -full-history -min-match-id=6000000000
```

`-full-history` игнорирует сохранённую границу и просматривает историю до `-min-match-id`. Уже сохранённые матчи пропускаются.

### Загрузка метаданных

После импорта основных матчей выполните:

```sh
go run ./cmd/metadata-check
```

Команда обходит сохранённые матчи, использует `cluster` и `replay_salt` из исходного ответа GC, загружает `.meta.bz2`, распаковывает данные и сохраняет JSON в БД. Между началами запросов выдерживается интервал не менее пяти секунд. Для повторной загрузки используется та же команда: существующие метаданные обновляются.

Метаданные — отдельный источник, а не полная демка `.dem`. Их наличие и заполненность зависят от конкретного матча; команда может завершать отдельные загрузки с ошибкой. Сейчас загрузка метаданных запускается отдельно от `gc-check`.

## HTTP API

| Метод | Маршрут | Результат |
| --- | --- | --- |
| GET | `/api/health` | Состояние HTTP-обработчика без проверки БД |
| GET | `/api/matches?limit=20&offset=0` | Сохранённые матчи от новых к старым |
| GET | `/api/matches/{id}` | Подробности матча |
| GET | `/api/matches/{id}/purchases` | Покупки игроков по времени |
| GET | `/api/matches/{id}/inventory` | Снимки инвентаря и личная ОЦ |
| GET | `/api/matches/{id}/graphs` | Графики и события смертей из метаданных |
| GET | `/api/players/avatars?account_ids=123,456` | Аватарки, до 10 Account ID за запрос |
| GET | `/api/players/{id}/profile` | Профиль и ранг по Dota Account ID; источник OpenDota/STRATZ |

GET-маршруты также поддерживают HEAD. Для списка API по умолчанию использует `limit=20`, допустимы значения от 1 до 100; `offset` — неотрицательное целое число. Это серверный предел, а интерфейс истории предлагает шесть фиксированных размеров и по умолчанию выбирает 5.

В маршрутах матчей `{id}` — внутренний ID PostgreSQL из списка, а `dota_match_id` — отдельный внешний ID Dota 2. В маршруте профиля `{id}` — Dota Account ID. Время начала передаётся в UTC, длительность — в секундах; неизвестные показатели — `null`, известный ноль — `0`.

Ошибки имеют объект `error` с `code` и `message`. Основные статусы: `400` — неверные параметры, `404` — матч или маршрут не найден, `405` — неподдерживаемый метод, `500` — ошибка чтения или обработки данных. Отсутствие метаданных отображается как недоступность соответствующих данных.

Контракты: [основной API](docs/api.md), [покупки](docs/api-match-purchases.md), [инвентарь](docs/api-match-inventory.md), [графики](docs/api-match-graphs.md), [профили](docs/api-player-profile.md). Некоторые документы описывают исходное предложение; актуальные маршруты зарегистрированы в `internal/http/router.go`.

## Docker и CI/CD

В репозитории подготовлены:

- `Dockerfile` — сборка HTTP-сервера и `gc-check`, включая статические файлы сайта.
- `compose.yaml` — PostgreSQL, веб-сервер, Caddy с HTTPS и отдельный импортер в профиле `import`. Веб-порт хоста привязан к `127.0.0.1`; публичный доступ предусмотрен через Caddy.
- Постоянные тома для БД, Steam-токенов и данных Caddy.
- `deploy/` — сценарии обновления, импорта и systemd-таймер. Импорт и деплой используют общую блокировку.
- `.github/workflows/deploy.yml` — проверки Go/JS, публикация Docker-образа в GHCR и условный деплой на VPS при `DEPLOY_ENABLED=true`. Нужны предварительно настроенные переменные, секреты и конфигурация VPS.

Compose читает конфигурацию из `/etc/dota-stats` (путь можно изменить через `DOTA_CONFIG_DIR`): `db.env`, `web.env`, `importer.env`; сценарии релиза также используют `release.env`. При первом создании БД Compose подключает четыре начальные миграции; для существующего тома изменения схемы нужно применять отдельно.

Текущий Docker-образ не включает `metadata-check`. Наличие файлов развёртывания само по себе не подтверждает успешный запуск CI/CD и работу продакшена.

## Проверки

```sh
go test ./...
node --test web/tests/*.test.cjs
```

Тесты фронтенда запускаются без установки npm-зависимостей. Они проверяют аналитику, балансировщик, покупки, инвентарь, прокачку, графики, рекорды, избранное и пагинацию. Интеграцию с PostgreSQL, Steam и доступность данных конкретных матчей проверяйте отдельно.

## Структура проекта

| Путь | Назначение |
| --- | --- |
| `cmd/server/` | HTTP API и раздача сайта |
| `cmd/gc-check/` | Импорт матчей через Steam/GC |
| `cmd/metadata-check/` | Отдельная загрузка метаданных сохранённых матчей |
| `internal/config/` | Конфигурация |
| `internal/http/` | Роутер, обработчики, DTO и преобразование данных |
| `internal/repository/postgres/` | Матчи, участники, метаданные и прогресс синхронизации |
| `internal/source/` | Клиенты Steam/GC и загрузки метаданных |
| `web/` | Фронтенд без отдельной сборки и его тесты |
| `migrations/` | SQL-миграции |
| `deploy/` | Развёртывание и плановый импорт |
| `testdata/` | Локальные примеры данных |
| `docs/` | Контракты, исследования и планы |
| `main.go` | Старая учебная версия без PostgreSQL |

Старая версия запускается командой `go run .`, читает `testdata/match.json` и использует порт `8080`. Основное приложение запускается через `go run ./cmd/server`.

## Планы

Админ-панель с очередью задач PostgreSQL, входом через Steam и сохранением входа, добавлением аккаунтов и выбором режима импорта: новые матчи после сохранённого прогресса или история до заданного ID. Далее — загрузка, скачивание и разбор демок, MVP, расширенные события и карты, сверка предварительных графиков и дальнейшая доработка интерфейса. Эти возможности ещё не реализованы.
